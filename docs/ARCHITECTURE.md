# Архітектура веб-застосунку: Cloud Media Converter & Archiver

## 1. Загальний огляд системи

Веб-застосунок призначений для обробки ресурсомістких (CPU-bound) задач користувачів: конвертації медіафайлів (зображення, аудіо/відео) та стиснення/архівації файлів з різними алгоритмами високої ентропії.

Система побудована за розподіленою мікросервісною архітектурою з балансуванням навантаження, пулом воркерів, асинхронною чергою завдань та онлайн-інформуванням клієнта про прогрес.

## 3. Відповідність вимогам технічного завдання (TASK.txt)

| Пункт з TASK.txt | Вимога | Реалізація в системі |
| :--- | :--- | :--- |
| **Пункт 1** | Обмеження трудомісткості задачі (розмір, час). Відмова у разі перевищення. Перевірка на клієнті. | • **Клієнтська валідація:** розмір файлу ($\le 30$–$50$ МБ), тривалість/роздільна здатність.<br>• **Серверний ліміт:** жорсткий таймаут виконання задачі (наприклад, макс. 60–120 с) та ліміт на розмір розпакованих даних. При перевищенні — статус `FAILED_TIMEOUT`. |
| **Пункт 2** | Інформування про хід виконання (відсоток/етап). | • SSE (Server-Sent Events) або WebSocket.<br>• Воркери транслюють прогрес (0–100%) та поточний етап: `Аналіз файлу` $\rightarrow$ `Конвертація/Стиснення` $\rightarrow$ `Фіналізація`. |
| **Пункт 3** | Історія результатів, стан поточної задачі, скасування, запуск нової, ліміт задач. База даних. | • БД зберігає задачі зі статусами: `QUEUED`, `PROCESSING`, `COMPLETED`, `CANCELLED`, `FAILED`.<br>• Користувач може зупинити виконання задачі (сигнал скасування через Redis $\rightarrow$ воркер перериває підпроцес).<br>• Ліміт: не більше $N$ активних задач на одного користувача одночасно. |
| **Пункт 4** | Авторизація клієнта (HTTPS). | • Реєстрація / Логін з JWT-токенами.<br>• Nginx налаштований з самопідписаним або Let's Encrypt SSL-сертифікатом (порт 443 HTTPS). |
| **Пункт 5** *(Ключовий)* | Балансування навантаження мінімум для 2-ох серверів (Load Balancer). | • Nginx як Reverse Proxy / Load Balancer балансує HTTP/HTTPS та WS запити між двома або більше екземплярами `API Server 1` та `API Server 2`. |
| **Пункт 6** *(Бонус)* | Інформування про чергу та приблизний час очікування, якщо ресурси вичерпані. | • Якщо всі воркери зайняті, задача отримує статус `QUEUED` з номером позиції в черзі.<br>• Розрахунок приблизного часу очікування: $\text{ETA} = \text{Позиція в черзі} \times \text{Середній час задачі} / \text{Кількість воркерів}$. |
| **Пункт 7** *(Бонус)* | Горизонтальне розширення (автоматичний запуск нових контейнерів/серверів). | • Моніторинговий скрипт/сервіс стежить за довжиною черги в Redis: якщо черга $> K$ задач довше 10 секунд — відправляє виклик до Docker API на масштабування `docker-compose scale worker=N` (з обмеженням `max_workers`). |
| **Пункт 8** *(Бонус)* | Панель адміністратора для моніторингу процесів і навантаження. | • Окрема вкладка або дашборд `/admin`:<br>  - Кількість активних воркерів та їх CPU/RAM utilization.<br>  - Поточний стан черги (активні, очікуючі, завершені).<br>  - Таблиця живих процесів з можливістю примусової зупинки. |

## 4. Специфікація обчислювальних задач (Compute Tasks)

### А. Модуль конвертації медіа (Media Converter)
1. **Зображення (ImageMagick / Pillow / Sharp):**
   - Формати: PNG, JPG, WebP, AVIF.
   - Опції: якість (1–100%), зміна роздільної здатності (resize), алгоритми квантування.
   - Чому CPU-intensive: кодування в AVIF або важкий WebP вимагає значних математичних обчислень над матрицями пікселів.
2. **Аудіо / Короткі відео (FFmpeg):**
   - Конвертація MP4 $\rightarrow$ GIF (оптимізація палітри кольорів), MP4 $\rightarrow$ WebM, MP3 $\rightarrow$ OGG.
   - Чому CPU-intensive: перекодування кадрів відеопотоку.

### Б. Модуль компресії та архівів (Archive Studio)
1. **Стиснення файлів та папок:**
   - Алгоритми: `zip` (стандарт), `tar.gz` (середній), `7z / xz` (важкий CPU LZMA2 з рівнями стиснення 1–9).
2. **Генератор синтетичного тестового набору:**
   - Кнопка швидкого тестування: створити на сервері тестовий файл (10–50 МБ) заданої ентропії для демонстрації навантаження без тривалого завантаження через браузер.

## 5. Компоненти системи та стек технологій (Рекомендований)

- **Балансувальник:** Nginx (Reverse Proxy, SSL termination, Round-robin / Least-connected).
- **Бекенд (API сервери 1 і 2):** Python FastAPI або Node.js Express/NestJS (легкий, асинхронний, зручна робота з WebSocket / SSE).
- **Черга завдань:** Redis (Celery / RQ для Python або BullMQ для Node.js).
- **Обчислювальні воркери (Workers):** Окремі фонові сервіси, запущені в Docker-контейнерах з встановленими утилітами (`ffmpeg`, `p7zip`, бібліотеки обробки).
- **База даних:** PostgreSQL або SQLite (для спрощення локального розгортання) + ORM (SQLAlchemy / Prisma).
- **Фронтенд:** Сучасний веб-інтерфейс (React/Vite або чистий SPA на Tailwind CSS + Vanilla JS/Alpine.js) з інтерактивними індикаторами прогресу, Drag & Drop завантаженням та адмін-панеллю.
- **Оркестрація:** Docker Compose (дозволяє підняти всю інфраструктуру однією командою `docker compose up --build`).
